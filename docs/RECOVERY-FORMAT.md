# Encrypted recovery format

The codec is the foundation for application-data recovery. Settings now exposes a wallet-verified encrypted export of contacts, local notes, private display-name choices, receipt preferences, legacy blocked-address preferences and any upgraded legacy sync metadata. A reviewed restore flow now applies these same bounded data classes with a retained pre-restore backup. It does not collect arbitrary browser storage or establish protocol-history continuity. Default domain forwarding remains disabled until the complete recovery and launch acceptance checks pass.

`apps/web/src/recoveryArchive.ts` continues to accept the explicit version-1 data object: source label, wallet address, creation time, contacts, saved notes, wallet-attributed blocks, and protocol/network-scoped read-receipt preferences. All fields are required; unsupported fields and duplicate record identifiers are rejected rather than discarded. Addresses are normalized to lowercase. Limits are 1,000 entries per collection, 50,000 characters per note, 512 KiB of UTF-8 payload and 704 KiB of file input. Callers must report limits and retain original data; silently truncating an export is unacceptable.

Chat exports without upgraded sync metadata use payload version 2 with one additional required field, `localDisplayName`: a bounded string (including an explicit blank to show the wallet address) or null (no override; retain the ENS fallback). The field is accepted only for the Chat source. Version-1 payloads remain unchanged and cannot set a name; old clients reject version 2 rather than silently dropping it. The encrypted envelope and authenticated algorithm context remain version 1; the independent payload schema version is inside authenticated ciphertext. No public profile, publication consent or arbitrary storage field is included.

Exports with upgraded sync metadata use payload version 3. It adds required `syncPayload` and `syncMinimum:1|2` for the Chat source only; the private-name choice is optional when unknown in an older pre-restore backup. The full strict sync model preserves per-item timestamps, saved-item deletion, unblock and receipt-reset markers. Its visible preferences must match the archive's separate preference fields. Sync maps have their own 10,000-entry/300,000-byte model bounds; the combined archive still has the 512 KiB limit. Existing version1/2 files remain accepted. Unknown versions and inconsistent fields are rejected without rewriting the source.

The envelope uses Web Crypto AES-256-GCM with a random 96-bit nonce, 128-bit authentication tag, random 128-bit salt and PBKDF2-HMAC-SHA-256 at 600,000 iterations. Version/algorithm/work-factor parameters are fixed and authenticated as additional data; unsupported parameters fail before derivation. The work factor follows [OWASP's PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Passwords must contain 12–1,024 characters and must not be only whitespace; callers should encourage a unique high-entropy passphrase. There is no password reset or server escrow. No wallet address, contact, note or preference is exposed outside encryption. A passphrase holder can construct another valid file: encryption does **not** authenticate its asserted source or prove wallet ownership.

Both functions are side-effect free with respect to storage and network. Password bytes and plaintext byte buffers are cleared where possible; JavaScript strings and garbage-collected copies cannot be reliably erased. Keys are non-extractable. The module neither exports nor accepts raw storage snapshots, private keys, reusable signatures, sessions, sync grants, XMTP databases, membership authority or email-forwarding consent.

## Recovery caller contract

- Independently prove the selected wallet's ownership and pass that wallet to decryption. A file's claimed address or a provider's account list alone is not proof. Recheck the active wallet and operation generation after asynchronous work, before presenting/applying results.
- Collect only explicitly supported application fields for that wallet. Legacy origin-wide preferences require explicit attribution before conversion. Unmapped receipt IDs must remain recoverable at their origin; never guess a network or conversation mapping.
- Preview the records and require explicit restore intent. Imported strings remain untrusted plain text. Receipt-sharing changes require review; no restored value may automatically enable sync, tracking, mailbox access or bridge forwarding.
- Define deterministic duplicate/conflict handling and durable recovery before changing local data. Preserve originals, distinguish quota failures from success, and handle wallet switching, interruption and retry. The codec performs no merge or deletion.
- Keep organization configuration, per-conversation read state, delivery receipts and actual protocol history under their separate validated migration contracts. They are not silently included by this format.
- Never put an archive, passphrase, signature or key in a URL, analytics event, log or unencrypted transfer channel. File handling must check size before reading. Recovery is incomplete until old/new-device and browser acceptance passes.

Focused tests exercise real encryption, Unicode and large-file round trips, randomized exports, tampered salt/nonce/ciphertext, wrong wallet/password, encrypted invalid payloads, unsupported KDF parameters, schema injection, ambiguous duplicates and resource bounds.

## Current local-data export

The Settings card exports the current wallet’s contacts and local notes from the dedicated IndexedDB store, plus the private display-name choice, receipt preferences and legacy blocked-address preferences. Older settings-only archives contain empty contacts/notes. Empty collections are not deletion instructions; restore never infers deletion from absence. It does not export usable sync authority, keys, grants, XMTP history, organizations or raw storage. Version3 also includes legacy synchronized items and their deletion history; its stored sync preference never authorizes a resumed session. A fresh two-minute challenge binds the wallet, browser origin, chain, random nonce and export purpose. EOA signatures are verified locally; contract-wallet signatures use viem’s mainnet verifier through the configured RPC (including supported ERC-1271/ERC-6492 paths). Other contract-wallet chains fail closed. No signature is cached.

Accounts, chain, provider identity, disconnect events, component lifetime, the selected preferences and exact settings record (including sync metadata), exact private-name storage value and the local-data revision are rechecked across asynchronous work before releasing the file. Unresponsive provider calls time out at the challenge deadline. Passphrase fields clear after the attempt; no password or private data enters a URL, log or storage. The card opts out of Insights interaction tracking. Browser tests decrypt the actual download, confirm unchanged storage, and exercise signature refusal, disconnect and preference changes during encryption. Mainnet contract verification has mocked boundary coverage; real contract-wallet/device acceptance remains outstanding.

## Local contacts and notes

Chat offers private contact labels through Chats and compose, and a separate Local notes view in Chats. Existing Saved Messages protocol conversations are preserved. Selecting a contact fills compose; it sends nothing and publishes no profile. Contacts and notes are wallet-partitioned browser data, not server authorization or proof of ownership. They are not encrypted at rest or automatically synced; the UI discloses this and offers the encrypted export above. Shared browser profiles are not a private multi-user vault.

`chat-local-data-v1` IndexedDB stores one versioned record per lowercase wallet in `wallets`. Strict schema, count and payload bounds reuse the recovery validator. Unsupported/malformed stored data blocks writes; it is never reset to empty. Read/validate/item-compare/write happens in one transaction, with success reported only after commit. Independent additions from tabs are retained; stale edits/deletes and duplicate additions fail with input preserved. Refresh notifications contain no wallet or content. Focus/visibility refresh works without BroadcastChannel. Forms display imported text as text, exclude interaction analytics, and reset on wallet changes.

Reviewed restore is available for supported recovery archives. Governance/Research source exporters, end-to-end source migration acceptance, production protocol-history acceptance and public-profile controls remain separate unfinished work. Local records and retained recovery backups are not encrypted at rest.

## Settings persistence prerequisite

Preferences now retain their established `chat:settingsPrefs:v1:<scope>` key and flat preference fields, with an optional `updatedAt` field committed in the same `setItem`. Upgraded records also hold full `syncPayload` and a monotonic `syncMinimum`; each preference edit updates only actual changed fields and retains other metadata. Prepared upgrades use minimum1 until upgraded remote data is confirmed; minimum2 cannot be lowered by a later merge. The older separate timestamp remains read-only fallback data. Existing valid partial records are accepted without a mount-time rewrite; malformed, unsupported or unreadable records are preserved and block changes/export/sync until storage is repaired and the app reloaded. This prevents defaults from overwriting recovery evidence.

A failed preference write keeps the committed selection and displays a persistent, translated error. Sync cannot report enabled when saving its preference fails. Stopping or revoking sync still clears this session's authority even if the opt-out cannot be persisted, with a distinct partial-result message. Pending encryption/timers respect storage failure. Raw-record comparison detects changed preferences. All current preference, private-name and contact/note writes participate in the same per-wallet Web Lock used by restore. Receipt controls expose a saving state and acknowledge persistence before becoming editable again. This does not create a cross-store database transaction. Other legacy storage helpers are outside this change.


## Reviewed restore and interruption recovery

`SettingsRestore` checks file size before reading, verifies the connected wallet with a purpose-bound one-use challenge, decrypts for that wallet and previews incoming contacts/notes and preference choices. Apply requires a fresh ownership check. Duplicates are skipped; conflicts keep existing values unless individually selected for replacement. Receipt preferences and additive legacy blocks each require explicit opt-in. Legacy block preferences do not change XMTP/Push consent. Missing entries never delete data. A file's source label remains an unverified claim, and imported strings render as text. Combined limits are validated without truncation.

The journal uses the reserved `restore:<lowercase-wallet>` key in the existing IndexedDB `wallets` store, preserving ordinary records and database version 1. It contains strictly validated before/after local-data snapshots and preference values, stable operation identity, claimed source and phase. It never contains a passphrase, credential, wallet key, sync grant or arbitrary storage dump. A bounded one-backup-per-wallet policy prevents silent replacement: users can download an encrypted pre-restore archive and must explicitly discard the retained backup before another import.

Preparation persists the full journal before changing any user records. A `v1:<operation-id>` marker at `<wallet-settings-key>:recovery-pending` prevents ordinary writes until reconciliation finishes. Web Locks serialize cooperating current tabs; locks time out while queued. Refresh other Chat tabs to load current code before using restore. Old scripts and manual storage tools cannot be forced to participate; exact snapshot comparisons reject unexpected later states rather than overwriting them. Web Locks support is required for coordinated local writes; unsupported clients fail closed. Physical-device/native acceptance remains outstanding.

Apply atomically writes the local-data target plus a pending journal, writes the expected preference target, verifies both stores and commits the completed phase before removing the marker. This is a recoverable multi-step operation, **not** an atomic transaction across IndexedDB and localStorage. A failed or interrupted step stays pending. Reload and Resume reconcile only recognized original/target values, without duplicate entries or repeated revisions. Undo similarly journals its progress and refuses later edits; the original backup remains available for a separate merge. If an external change conflicts with a pending operation, an explicitly confirmed Stop action can retain current validated data and the backup while marking the import abandoned, never completed. An orphaned preparation marker can be cleared only after verifying that no journal exists.

Receipt sharing and this browser's sync authority are paused during recovery, including after reload and in current peer tabs. Apply/undo keep sync off; archives do not authorize tracking, mailbox access, bridge routing or memberships. Only a verified completed local result is reported as saved. Damaged journal/storage records are preserved, not reset. The recovery UI is excluded from interaction analytics and passphrase inputs clear after each attempt.

Browser acceptance covers reviewed conflicts and explicit preference choices, real encrypted backup downloads, wrong wallets/damaged/oversized files, backup-transaction failure, partial preference/final-journal writes, interrupted undo, reload/resume, stale undo, competing tabs, disconnect while queued and explicit abandonment with current data and the backup retained. Unit coverage verifies strict journal/merge validation, purpose-bound signatures, receipt suspension and missing Web Locks.

## Private display-name recovery

A version-2 file previews the current and incoming choices, explicitly distinguishing blank from default/ENS. Its name checkbox starts unchecked; neither a v1 import nor a declined checkbox changes the name. Apply checks the exact reviewed storage value under the shared wallet lock. A malformed local value blocks v2 export/review rather than becoming an ENS opt-in or being discarded.

When the name is selected, journal version 2 retains only its exact before/after raw values in addition to the established fields. The existing database and pending marker remain compatible; version-1 journals still resume without touching names. Reconciliation checks all recognized states before changes, writes preferences and then the private name, and verifies both before finalizing. Label storage failures remain pending and resume without repeated local-data revisions. Undo restores the original blank/default/custom choice and refuses a later name edit. Backups include the original choice as an encrypted v2 payload. A new name edit uses the same lock, refuses a pending recovery, and checks wallet-session generation after acquiring a queued lock. This remains recoverable multi-store reconciliation, not an atomic transaction across stores.

Browser coverage includes all three name choices, unchanged public-profile publication, original-name backup/undo, default opt-out, legacy imports, cross-tab edit conflicts, partial storage/resume, pending-edit rejection, queued disconnect and changes during encrypted export. Physical-device and real old/new-origin acceptance remain separate.


## Separate settings-sync compatibility boundary

Enabling encrypted settings sync upgrades its separate payload to format2 under the guarded API boundary described in [SYNC-FORMAT-UPGRADE.md](SYNC-FORMAT-UPGRADE.md). Archive3 carries that full model, but restores never enable sync authority. Unsupported encrypted data or API capability pauses writes and preserves existing data. An older local snapshot cannot replay deleted entries after the remote wallet has upgraded.

The version3 restore checkbox for legacy synchronized items/deletion history starts unchecked. Receipt preferences and additive blocks keep their separate explicit choices. Import merges full metadata, then applies only the reviewed preference choices; declining metadata import preserves existing markers. Version3 journals retain complete before/after/undo metadata and reject floor downgrade or dropped history. Undo expresses newer explicit intent, including restoring a selected deleted item or deleting an item added by the import, while retaining earlier markers and keeping sync off. Backups include full pre-restore metadata; an unknown private-name choice stays absent rather than becoming a default-name instruction. Local sync metadata and recovery journals are not encrypted at rest; exports and remote sync are encrypted.

Browser coverage includes version3 preview, encrypted export/decrypt, reload/undo, declined import and interrupted undo. Two-device sync tests exercise deletion replay, explicit old-device preference choices and uncertain first writes. Production-origin, native and physical-device recovery acceptance remains outstanding.
